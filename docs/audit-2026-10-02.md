# Rejgau code and deployment audit

Audit date: October 2, 2026. Observation times use Pacific Daylight Time unless marked UTC.

The audit found 22 reproducible code defects in event capture, publication, rendering, and build tools. Two findings need priority attention. A retry failure can quickly remove valid events from normal archive processing. Deleted originals can remain visible inside generated reply previews.

The current deployment was processing its small archive without a backlog at the time of inspection. This snapshot does not remove the reproduced failure cases. The deployed Worker bundle matches the locally built audit bundle byte for byte. The deployed reader uses an older source revision that lacks the merged cache-refresh fix.

The report separates confirmed defects, deployment observations, and architectural concerns. GitHub issues accompany every confirmed code defect. No application source, archive content, production configuration, or deployment changed during the audit.

### Deployment findings

D1, P2: The deployed reader omits the existing cache-refresh fix. `REJGAU_REF` pins `ac3c246`, while [PR 4](https://github.com/int19h/rejgau/pull/4) is already merged into audited source. Public HTML still requests unversioned JavaScript and CSS. Those responses and the search JSON permit ten minutes of browser caching.

Returning browsers can therefore retain old data or bundles after publication. Archive, logs, and Pages still match the same source archive commit. This finding concerns browser refresh behavior rather than missing archive commits. Update the pinned renderer revision through the normal release process. Make sure that the published HTML uses versioned assets afterward.

D2, operational uncertainty: Live observability configuration differs from the repository. The API returns `observability.enabled: false` together with `observability.logs.enabled: true` and `persist: true`. The repository sets the top-level flag to true. The stored-log query returned HTTP 403 with `Authentication error`.

The audit cannot establish effective log persistence from these conflicting values. Make the intended logging configuration explicit and establish read access for incident investigation. Do not interpret unavailable logs as evidence that no errors occurred. [Cloudflare Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/).

D3, optional hardening: The archive repository has no branch protection, rulesets, or Pages environment protection rules. Existing writers can change publication inputs without another review gate. The audit found no unauthorized change. Protect the default branch and publication process if that matches the collaboration model. Preserve the bot's archive writes and the deliberate logs force push.

These deployment observations do not create duplicate code issues. D1 already has a source fix. D2 and D3 concern operational configuration and access policy.

## Security interpretation

The main security-relevant defects affect publication filtering, availability, and local build boundaries. R1, R6, B1, and S1 violate limits on generated or sanitized output. A1 lets a stalled media source delay unrelated archive writes. B3 lets a crafted raw archive escape the requested output directory.

The raw archive deliberately retains deleted text and edit history. R1 and R6 concern suppression from generated views, not access to previously inaccessible Discord channels. B1 affects reused output directories, while the deployed workflow builds into fresh directories. B3 requires a modified or untrusted raw archive because ordinary Discord users cannot choose channel IDs.

S1 follows from documented payload shapes and a synthetic reproduction. The audit did not observe private moderation flags in the live archive. These distinctions limit the claims and guide the repair priority.

Useful controls are already present. Admin authentication hashes both values before a constant-time comparison and accepts the key through headers. SQL values use bound parameters. GitHub installation tokens target the configured repository, and archive commits never force-push.

The renderer escapes ordinary text and restricts links to permitted URL schemes. Its Content Security Policy restricts scripts and media origins. No direct script injection emerged from source inspection or local browser probes.

The workflow pins action revisions and separates publishing permissions from dependency builds. Checkouts do not retain credentials, and CI disables package installation scripts. The deployed renderer also pins a source revision, although that revision currently trails the merged fix.

An aggregate inspection of the small live raw archive found no token, authorization, email, phone, or component custom-ID fields. That inspection does not prove complete privacy filtering. It also does not inspect media bodies or compare the archive against Discord itself.

## Confirmed defects

### G1 Respect pending Gateway retry delays before quarantining events

GitHub issue: [#5](https://github.com/int19h/rejgau/issues/5).

Priority: P1. Valid events can leave the delivery queue during a brief downstream outage.

Every incoming dispatch calls [kickPump()](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/gateway.ts#L239-L247). That method tests whether a pump is active, but ignores its pending retry timer. After a failed attempt returns, another dispatch immediately retries the same row. Heartbeat alarms also enter this path.

The [failure handler](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/gateway.ts#L280-L304) quarantines an event after 100 transient failures. The source describes that threshold as [roughly eight hours](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/gateway.ts#L31-L36). Incoming traffic can exhaust it within seconds.

Reproduce this in the Cloudflare worker test runtime:

1. Create a Gateway object with a configured guild and a fixed session ID.
2. Replace its downstream `GUILD` stub with an `ingest()` implementation that always returns `{handled: 0, failed: {retryable: true, error: "temporary network failure"}}`.
3. Deliver 100 `MESSAGE_CREATE` dispatches with increasing sequence numbers. Let each pump attempt finish before the next dispatch. Keep the first retry timer pending.
4. Read Gateway status and the downstream call count.

Expected: the first failure schedules a delay. Subsequent dispatches remain queued until that delay expires.

Actual: the isolated probe makes 101 downstream calls, leaves 99 queued rows, and records one dead letter in under five seconds.

A dead letter is an event removed from normal delivery. SQLite retains it, but no supported endpoint replays it. The GitHub archive therefore omits the event after service recovers.

Persist a retry deadline and attempt count. Make all pump entry paths respect that deadline. Add a supported recovery path for quarantined events.

### R1 Preserve deletion tombstones for messages known only through reply snapshots

GitHub issue: [#6](https://github.com/int19h/rejgau/issues/6).

Priority: P1.

A deleted original remains visible in generated reply previews when the archive never records that original as a standalone message.

The [delete handlers](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/tools/fold.ts#L273-L282) discard events for unknown message IDs. The [reply resolver](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/tools/fold.ts#L116-L121) then returns the embedded copy. The [site generator](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/tools/sitedata.ts#L151-L162) publishes that copy as current content.

Reproduce with synthetic archive records:

1. Select channel `11` with `backfill:false` and an existing older message `1554541602075316245`.
2. Record a new reply whose `referenced_message` contains that original, with content `original text`.
3. Record `MESSAGE_DELETE` for the original ID, then rebuild the reader data.

Do not add a separate `MESSAGE_CREATE` record for the original. This models a reply to a message that predates archive collection.

Expected: the generated reply contains `referenced:{deleted:true}` and omits the original text. Actual: its `referenced.content` still contains `original text`. The audit reproduced this sequence without concurrent requests or reordered events.

This violates the rule that generated views exclude deleted content. Raw archive records intentionally remain public. This finding concerns suppression from generated views, not newly exposed private Discord channels or an authentication bypass.

Store deletion tombstones, records that retain deleted message IDs, independently of message snapshots. Consult them during reply resolution and later snapshot insertion. Add coverage for single deletes, bulk deletes, and replies to originals that were never backfilled.

### A1 Bound external media requests so a stalled image cannot block guild commits

GitHub issue: [#7](https://github.com/int19h/rejgau/issues/7).

Priority: P2.

A stalled external image request blocks all scheduled commits for its guild. Administrative flushes also return a busy error during the request.

[Media extraction](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/media.ts#L40-L53) accepts arbitrary HTTP and HTTPS hosts. The [alarm handler](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L657-L678) awaits media work before it flushes pending messages. Neither the [download](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L822-L832) nor the [stream read loop](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L855-L866) has an application deadline.

Reproduce locally with the existing workerd test environment and `installFakes()`:

1. Initialize a configured guild with one selected text channel and pending messages.
2. Ingest a message whose embed image URL is `https://slow.example/image.png`.
3. Replace `fetch` for that URL with a response promise controlled by the test.
4. Start `GuildArchive.alarm()` inside `runInDurableObject()`.
5. Wait until the fake image request starts.
6. Read the guild status and call `flushNow()` while the response remains pending.
7. Resolve the fake request with a small valid image response.

Actual: the request has no AbortSignal, pending lines remain uncommitted, and `flushNow()` returns `{error:'busy; try again'}`. After the image response resolves, the same alarm commits those lines. A passing local probe reproduced this sequence against the linked revision.

Expected: an external image cannot postpone unrelated log commits beyond a bounded application timeout.

This creates an availability risk through message media. [Cloudflare limits alarm invocations to 15 minutes](https://developers.cloudflare.com/workers/platform/limits/#duration). The probe demonstrates the stall, not an indefinite execution or the exact runtime termination behavior.

Add deadlines that cover response headers and body consumption. Keep due log commits independent from media completion, and record retryable media timeouts.

### A2 Retry transient Discord failures when refreshing expired attachment URLs

GitHub issue: [#8](https://github.com/int19h/rejgau/issues/8).

Priority: P2.

A transient Discord error permanently fails an attachment when its original signed URL expires. The item bypasses the normal media retry policy.

The [attachment refresh path](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L822-L832) catches every error from the message request and replaces it with `null`. It then creates a synthetic HTTP 404 response. [The download result handler](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L835-L841) treats that response as final. [Media work](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L794-L815) records `MEDIA_FAILED` and changes the row status to `failed`.

Reproduce locally with the existing worker tests and `installFakes()`:

1. Initialize a configured guild with a selected text channel.
2. Pause automatic alarms for that guild.
3. Ingest a message with attachment URL `https://cdn.discordapp.com/attachments/11/91/expired.png` and a valid message ID.
4. Return HTTP 403 for `/attachments/11/91/expired.png` in the fake CDN.
5. Return HTTP 503 for `/api/v10/channels/11/messages/<message-id>` in the fake Discord API.
6. Call the existing `mediaWork()` method once through `runInDurableObject()` with the parsed guild configuration.
7. Read `GuildArchive.status()`.

Actual: status reports `mediaFailed: 1` and `mediaPending: 0` after this single attempt. A passing local probe reproduced those values against the linked revision. The failure record reports the synthetic 404 instead of the upstream 503.

Expected: the attachment remains pending with a retry time because Discord failed temporarily. A temporary outage must not masquerade as a missing message.

The same catch also covers network failures and exhausted rate-limit retries. Affected media stays absent until an administrator invokes `/retry-media`.

Preserve transient errors for `mediaWork()` to classify. Return a final missing result only after a definitive missing-message or missing-attachment response.

### A3 Wait for active archive work before acknowledging pause and report busy flushes as failures

GitHub issue: [#9](https://github.com/int19h/rejgau/issues/9).

Priority: P2.

The pause endpoint acknowledges success while an active alarm can still commit. A subsequent flush returns a busy error inside HTTP 200.

[setPaused()](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L1096-L1099) writes a flag and returns without waiting for active work. The [alarm handler](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L657-L670) reads the flag only when it starts. [flushNow()](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L1021-L1026) rejects concurrent work, but the [HTTP handler](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/index.ts#L70-L83) returns that error with the default success status.

Reproduce locally with the existing workerd tests and fake GitHub:

1. Initialize a configured guild with pending selected-channel messages.
2. Intercept the GitHub branch-read request and hold its response with a test-controlled promise.
3. Start an alarm and wait until that request begins.
4. Call `setPaused(true)` while the branch read remains pending.
5. Read the guild status and call `flushNow()`.
6. Release the branch-read response and let the alarm finish.

Actual: pause returns, status reports `paused: true`, and flush returns `{error:'busy; try again'}`. The alarm then commits after the pause acknowledgment. A passing local probe reproduced this sequence against the linked revision.

Expected: pause success provides an explicit boundary after active commits finish. A flush that cannot drain pending work returns an HTTP failure status or another unmistakable incomplete result.

The [documented history rewrite procedure](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/README.md#L181-L188) relies on pause followed by flush. The probe does not demonstrate redaction restoration after a successful complete drain. Its flush explicitly fails, and branch updates remain non-forced. The defect is the incomplete pause boundary and misleading HTTP success status.

Serialize pause with active work or wait for it before success. Preserve the explicit busy information at the HTTP layer.

### A4 Bound the pending SQL read before allocating a flush batch

GitHub issue: [#10](https://github.com/int19h/rejgau/issues/10).

Priority: P2.

The flush implementation loads every pending log line into memory before it applies its batch limit. Large queues therefore defeat the intended memory bound.

The [initial flush query](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L927-L944) calls `toArray()` without a SQL limit. Only after this allocation does the loop apply `MAX_FLUSH_BYTES`. It also measures JavaScript string length rather than allocated memory. The [file assembly step](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L950-L956) loads complete existing day files outside that budget.

Reproduce locally with the existing workerd test environment:

1. Initialize a configured guild and pause its automatic alarms.
2. Replace its pending test rows with 3,000 rows that share one archive path.
3. Set each row's line value to a string of 4,096 ASCII characters.
4. Wrap the real SQL cursor for `SELECT n, path, line FROM pending ORDER BY n`.
5. Count the rows returned by its existing `toArray()` call.
6. Invoke one `flush()` through `runInDurableObject()` with the normal fake GitHub client.
7. Read the materialized row count, committed count, and remaining pending count.

Actual: one flush materializes all 3,000 rows, commits 2,049, and leaves 951 pending. A passing local probe reproduced these counts against the linked revision. The probe measures allocation scope and does not deliberately cause memory exhaustion.

Expected: a flush reads only the rows that fit its bounded batch, with allowance for existing files and serialization.

A long pause, backfill, or GitHub outage can produce a much larger queue. [Cloudflare documents a 128 MB memory limit per isolate](https://developers.cloudflare.com/workers/platform/limits/#memory). Repeated full allocations create a recovery risk when the queue approaches that limit.

Iterate or page the SQL cursor before materialization. Include existing file contents in the budget, and split oversized archive files when necessary.

### A5 Scope durable release caches to the configured GitHub repository

GitHub issue: [#11](https://github.com/int19h/rejgau/issues/11).

Priority: P2.

Changing a guild's destination repository leaves its durable release cache associated with the previous repository. The new GitHub client receives the old release ID.

[GitHub client selection](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L154-L159) creates a new client when `guild.repo` changes. The [configuration signature](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L466-L473) also includes the destination repository. However, [release selection](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L903-L922) caches IDs and counts under `releaseId:<tag>` and `releaseCount:<tag>`. Neither key includes the repository name.

Reproduce locally with the existing workerd tests and fake GitHub:

1. Initialize configured guild 106 with destination `o/r106`.
2. Ingest a message with an attachment created in September 2026.
3. Run media work until the fake repository contains its `media-2026-09` release.
4. Keep the same GuildArchive instance and durable storage.
5. Create the next guild configuration with destination `o/new-destination`.
6. Obtain its client through the existing `gh()` method.
7. Call `release()` for `2026-09` with that new client.

### R8 Show an unavailable-month state instead of loading forever

GitHub issue: [#26](https://github.com/int19h/rejgau/issues/26).

Priority: P3.

A route for an absent archive month remains in a permanent loading state, although the reader never sends a request for that month.

The [loading effect](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/reader/src/main.tsx#L103-L108) clears existing data and returns when `info.months[current]` is absent. The [view](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/reader/src/main.tsx#L133-L141) still renders `Loading…` because the route supplies a nonempty month value. It also provides no adjacent-month links when that month is missing from the manifest.

Reproduce with a local reader fixture:

1. Publish channel `22` with only `months:{"2026-09":1}` in its manifest.
2. Open the reader at `#/c/22/2026-08`.
3. Wait for the archive manifest and user table to finish loading.

Expected: the reader states that August is unavailable or empty and offers a valid month. Actual: the heading displays `August 2026` and the message pane remains at `Loading…`. No August request occurs, so waiting cannot resolve the state. The audit reproduced this behavior in Chromium.

This route does not require malformed input. A bookmark can become stale after the last published message in its month is deleted. A manually entered month produces the same result.

Treat an absent month as a completed empty or unavailable state. Provide a link to the nearest valid month or the latest month. Preserve the separate error state for requests that actually fail. Add coverage for both an absent month and a channel with no archived months.

## Architecture and maintainability

### Separate work so failures do not spread

The single Gateway is reasonable for one bot connection. Its delivery queue also enforces one global order across all guilds. A failure for one guild therefore delays every guild behind it. Preserve per-guild event order while letting healthy guilds progress independently. This matters as the deployment expands beyond its current single guild. See [the pump loop](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/gateway.ts#L250-L279).

`GuildArchive` combines permissions, selection, ingestion, recovery, media, GitHub writes, scheduling, and administrative state in 1,129 lines. Its `busy` flag and separate ingestion promise chain define different serialization boundaries. Pause participates in neither boundary. Define explicit lifecycle rules before extracting smaller modules. A single rule for pause, reset, ingestion, and active writes will reduce race conditions.

Optional media work currently precedes due log commits. This coupling causes A1 and makes archive latency depend on external media providers. Separate durable media jobs from log flush scheduling. Give external requests deadlines that cover response bodies, as well as headers.

### Persist recovery decisions and expose them to operators

Gateway retry counts and timers exist only in memory. Routine object restarts discard them, so the claimed retry duration does not survive a restart. Store retry deadlines and counters beside the queued event. Provide supported inspection and recovery for dead letters. These changes complement G1.

The REST client has no shared state for Discord rate limits across callers or guild objects. Fixing G3 preserves each response deadline, but it does not coordinate global restrictions. Track global and endpoint restrictions in a shared scheduler before adding more guilds.

The archive HTTP interface also returns some operational failures inside HTTP 200 responses. `/reset` catches every reset rejection before attempting a restart. That obscures the difference between the intended object abort and another reset failure. Make operation outcomes explicit and preserve unexpected errors. The audit did not reproduce a failed reset in production. See [admin handlers](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/index.ts#L56-L83).

### Define data contracts at each boundary

Discord payloads, raw records, folded state, and reader messages use many `any` values and unchecked casts. Related types also differ between tools and reader code. TypeScript therefore cannot establish that generated data matches consumer expectations. Define shared output types and validate external records before publication.

The privacy filter guesses object roles from field presence. S1 demonstrates the weakness for members. Thread-member notification flags also survive despite the stated removal of bot-specific fields. Filter sensitive fields using the event and parent-field context. Preserve explicit tests for every published object kind. [Discord thread-member fields](https://docs.discord.com/developers/resources/channel#thread-member-object).

`parseConfig()` accepts `backfill: "false"` as a truthy value. It also accepts JSON numeric overflow such as `1e400`, which becomes Infinity. Require explicit booleans, valid strings, finite numbers, and practical ranges. Reject invalid configuration before it reaches timers or path construction. These are demonstrated validation weaknesses, without a reproduced live operational failure. See [configuration parsing](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/config.ts#L59-L88).

### Bound memory and growing state

A4 defeats the intended flush memory bound. Other paths also assume small archives. Raw builds load, parse, sort, and fold the full history in memory. The reader retains loaded months and search files indefinitely and renders an entire month at once. Measure growth and introduce limits or incremental processing before this archive becomes large.

Media and member tables retain completed rows without indexes for their pending-work queries. Queue selection and status counts therefore scan growing histories. Add indexes for pending work and measure storage before choosing retention policies. No current deployment measurement shows this as a bottleneck. See [table definitions](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/src/archive.ts#L114-L124).

Release counts can drift after an upload succeeds but its response is lost. Separate guilds targeting one repository also maintain independent counters. Those conditions warrant rollover tests, but this audit did not reproduce an incorrect rollover. Keep them separate from the confirmed repository-ID cache defect A5.

### Treat publication as one complete generation

B1 shows why file-by-file replacement does not establish a complete publication. Generate output in a fresh directory and switch only after success. Validate all generated destinations before writing, which also addresses B3.

The source cache fix uses version query strings, but those strings do not create immutable files. A long-lived page retains its old manifest and can later fetch replacement files under the old query string. A generation directory or manifest refresh policy can make mixed-generation behavior explicit. This is a design concern, not a separately reproduced corruption case. See [reader loading](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/reader/src/data.ts#L64-L84).

The site and Markdown renderers separately implement message, component, media, and spoiler behavior. Share a typed publication model while keeping presentation code separate. Keep the privacy rules in that model so both outputs enforce the same policy.

The archive reader warns and skips malformed JSON lines. That produces a successful but incomplete build. Offer a strict mode or an explicit incomplete-build result for audit-sensitive publication. The input walker also follows directory symlinks without a cycle guard. Document the trusted-input boundary and reject unsafe structures when reading third-party archives. See [raw input loading](https://github.com/int19h/rejgau/blob/a03316ea26b1b67ab9e1a681c38330137a31b696/tools/build.ts#L23-L45).

### Strengthen tests and release provenance

The repository has useful unit and worker tests, but no committed CI workflow runs them. The Pages template builds outputs without running the complete application test suite. Add source CI for type checks and tests, with browser coverage for asynchronous navigation and failure states.

Existing fakes omit stalled responses, repository ownership of release IDs, full rate-limit delays, and several partial Discord payloads. Extend tests around behavior rather than copying implementation structure. The audit probes identify concrete missing cases and already reproduce the failures.

Record both renderer and archive revisions in generated metadata. Also record a Git revision with Worker versions. The audit established current Worker parity by downloading and comparing the bundle, which is more work than reading explicit provenance.

Documentation has minor drift. The README says ten failures before a dead letter, while source uses 100. The reader design describes 500 initial search results, while code uses 200. Poll voter tooltips are documented but absent. Update those descriptions when the related behavior receives tests.

## Known limits and unresolved questions

Archived-thread discovery is an explicit deferred feature. Current snapshots and history recovery cover active threads, so the audit does not file the documented omission as a defect. Lost sessions recover new messages but cannot reconstruct all missed edits, deletions, or reactions. These are documented collection limits.

Raw records and media releases intentionally retain deleted content. Removing data from the generated reader does not remove that source history. The report evaluates generated-view suppression separately from complete data removal.

Two source observations need focused follow-up. Fresh snapshots upsert channels without reconciling every absent stored channel. A newly configured idle guild can wait for another event before bootstrapping after a session resume. The audit did not reproduce a new-content privacy leak or lost-history case from these observations, so it does not file defect issues for them.

The audit lacks an independent Discord event inventory. It cannot prove that production captured every event. Stored application logs were unavailable because the read request returned an authentication error. Account billing, Discord application permissions, GitHub App installation permissions, and secret rotation history were not independently established.

The source and runtime tests cover the current platform configuration. They do not establish safety under every future Discord payload or package version. The small live dataset does not establish large-archive performance. No destructive, load, or exploit test ran against production.

## Repair order

Start with G1 and R1 because they affect archive completeness and current-view publication. Add the failing cases before changing their implementations. Then address A1, S1, B3, R6, and B1 to tighten availability, privacy, and output boundaries.

Next, repair media recovery, pause and stop semantics, full rate-limit waits, and flush memory bounds. Then address reader correctness and build portability. Keep each change small enough for source review and targeted tests.

Update the deployed renderer pin after the normal release review. Resolve the logging configuration and read-access ambiguity so future incidents have usable evidence. Do not attribute the observed platform disconnect outcomes to these defects without supporting logs.
